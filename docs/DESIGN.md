# DESIGN.md — 长程智能体工作流架构设计

> 配套文件：`docs/workflow.png`（带注释的工作流图）、`docs/plans/task.md`（任务定义 v2）
> 状态：设计稿 v1，待复核

## 0. 设计原则

1. **代码判定，智能体提议**：凡能用确定性代码判定的（指标计算、验收数值门槛、
   as_of 校验），绝不交给 LLM；LLM 只负责提出假设、诊断原因、评审裁决、撰写解释。
2. **产物单向流动**：每个阶段只读取上游产物、写入自己的产物目录；
   下游不可修改上游产物（文件系统层面只读约束）。
3. **一切可复现**：每次 run 的数据快照带哈希并锁定，同一 run 重放结果必须一致。
4. **小步失败**：错误在产生它的阶段被捕获和隔离，不扩散到下游。

## 1. 总体架构

```
                ┌─────────────────────────── 人类（Human）───────────────────────────┐
                │  H1 结构性改则批准   H2 终局验收   H3 数据异常处置                    │
                └───────▲───────────────────▲───────────────────▲────────────────────┘
                        │                   │                   │
  ┌─────────┐   提议   ┌┴────────┐  产物  ┌─┴─────────┐  产物  ┌┴───────────┐
  │Generator│ ───────► │Controller│ ───► │ Executor   │ ───► │ 确定性门禁   │
  │(LLM)    │ ◄─────── │(状态机)  │ ◄─── │(纯代码)   │ ◄─── │ (数值判定)   │
  └─────────┘  裁决    └─────────┘  裁决  └────────────┘       └──────┬───────┘
       ▲                                                            │
       │                                                     ┌──────┴───────┐
       └───────────────── 裁决/理由 ──────────────────────────│ Critic (LLM) │
                                                             │ 独立评审     │
                                                             └──────────────┘
```

Controller 是唯一的执行控制者（harness）：它驱动状态机、调用工具与角色、
执行门禁、写状态文件；Generator 与 Critic 不互相通信，只通过 Controller
交接产物（隔离二者上下文，保证评审独立）。

## 2. 角色与交接（要点 1）

### 2.1 角色表

| 角色 | 类型 | 职责 | 可用工具/权限 | 输入 | 输出产物 |
|---|---|---|---|---|---|
| **Controller** | 确定性代码（harness） | run 状态机、阶段调度、触发检测、重试、断点恢复、迭代计数、门禁执行 | 文件系统全目录读写；子进程调用；**无 LLM 能力** | state.json、事件（手动/自动/新数据） | state.json、调度日志、升级通知 |
| **Generator** | LLM 智能体 | 提出初始假设与修订版假设、诊断失败原因、撰写修订动机 | 只读 `runs/**`、`docs/**`；写 `inbox/hypothesis_<run_id>.json`（仅此一路径可写）；无网络权限 | 上一 run 的 metrics.json、verdict、任务定义 | hypothesis.json（参数/规则快照 + 动机说明） |
| **Executor** | 确定性代码（非智能体） | 取数、数据校验、信号生成、回测模拟、指标计算、基线计算、敏感性扫描 | akshare 网络（仅在②取数阶段开放）；只写 `runs/<id>/data`、`result` | hypothesis.json、数据快照 | 快照 CSV+哈希、trades.csv、equity.csv、metrics.json、sensitivity/ |
| **Critic** | LLM 智能体（独立上下文） | 对照验收标准逐项评审、排查未来函数与实现缺陷、检查稳健性、给出采纳/拒绝裁决 | 只读全部产物；**无任何写权限**（裁决经 Controller 代理落盘）；无网络权限 | metrics.json、auto_review.json、trades 样本、hypothesis 快照 | verdict（PASS/FAIL/ESCALATE）+ 逐条理由 |
| **Human** | 人 | H1 结构性改则批准、H2 终局验收、H3 数据异常处置 | 对话/CLI | 升级通知、终局产物 | 批准/否决决定 |

### 2.2 必须由确定性代码完成的计算

- 温度计上穿/下穿检测、交易信号生成与 t+1 执行的模拟撮合；
- 全部绩效指标（年化收益、最大回撤、夏普、交易次数）与买入持有基线的计算；
- 验收数值门槛的判定（§6.1 的五条标准逐条布尔值）；
- 阈值 ±5 敏感性扫描（每轮 5 组参数的回测）；
- as_of 校验（行情截至日 ≤ 信号截至日 ≤ 用户 as_of）、上市日自动确认；
- 数据快照 SHA-256 哈希与完整性校验；
- 迭代计数、阶段状态转移、超时控制。

### 2.3 分工边界

- **Generator 提议、Controller 执行**：Generator 输出的 hypothesis.json 只是
  提案；它无权触发回测或修改在跑 run。Controller 校验提案格式（schema）
  后才排入阶段队列。
- **Critic 评审、Controller 落盘**：Critic 无写权限，其 verdict 由 Controller
  原样写入 `review/critic_verdict.md`（保持原文，禁止润色），形成不可抵赖记录。
- **LLM 不可绕过门禁**：即便 Critic 说 PASS，验收仍以确定性数值门槛为准
  （Critic 只能 FAIL 一个数值达标的 run——防"评审放水"；反之数值不达标
  Critic 无权放行）。
- 两位智能体的系统提示均写明各自边界；违反边界的产物（写到非授权路径的
  文件）被 Controller 拒绝并记入日志。

## 3. 长程运行（要点 2）

### 3.1 runs/ 状态库结构

```
runs/
  manifest.json              # 全部 run 索引：run_id、hypothesis_id、阶段状态、verdict、时间戳
  champion.json              # 当前最优 run 指针（用于回归对比与回滚）
  inbox/                     # Generator 提案信箱（唯一允许 LLM 写入 runs 下的位置）
    hypothesis_<run_id>.json
  <run_id>/                  # 例：run-003
    hypothesis.json          # 假设快照：规则类型、阈值、版本号、父 run_id、动机
    data/
      snapshot_manifest.json # 输入清单 + 各文件 SHA-256 + as_of（信号末日/行情末日）
      signal.csv             # 从 xlsx 抽取的温度计序列（只读快照）
      price_hfq.csv          # 后复权日线快照
    result/
      trades.csv  equity.csv
      metrics.json           # 策略+基线全部指标
      sensitivity/           # 阈值±5 的 5 组 metrics
    review/
      auto_review.json       # 五条验收标准的确定性判定结果
      critic_verdict.md      # Critic 裁决原文（Controller 代笔落盘）
    state.json               # 已完成阶段列表、各阶段输入哈希、开始/完成时间、重试次数
    tmp/                     # 阶段工作区；阶段完成时原子重命名归档，中断残留可安全清理
```

### 3.2 阶段依赖与检查点语义

- 六阶段依赖链：①假设→②取数→③回测→④自动评审→⑤评审门槛→⑥修订→（回到①）。
- 检查点 = **（阶段产物存在）∧（state.json 中该阶段记录的输入哈希 == 当前输入哈希）**。
  两者皆满足即视为已完成，恢复时整段跳过；产物在而哈希不符（输入已变）则
  作废该阶段及全部下游产物重跑。
- 每阶段写入采用 tmp/ 暂存 + 原子改名，崩溃不会留下半个阶段的假完成态。

### 3.3 触发机制

| 触发 | 检测方式 | 动作 |
|---|---|---|
| 手动（主） | CLI：`python -m workflow run`（可带假设覆盖） | 新建 run 或恢复未完成 run |
| 未达标自动修订 | ④门禁或⑤裁决为 FAIL | Controller 自动从 state.json 续跑，Generator 生成 v(k+1) 假设；计数 +1 |
| 新数据到达 | ②取数时比对本地快照与源数据截至日 | 发现信号/行情已更新 → 生成"监控 run"：用 champion 假设在新窗口回测，对比旧结论是否反转，结论写入迭代日志 |

### 3.4 重试策略

- 瞬时故障（akshare 网络超时/限流）：指数退避重试，每阶段最多 3 次；
- 确定性阶段失败只重跑本阶段（输入哈希不变则产物可复用）；
- 数据质量故障（缺口、异常跳变、as_of 倒挂）**不自动重试**，阶段置 FAILED，
  升级 H3 人工处置；
- LLM 调用失败（Generator/Critic）：重试至多 2 次后升级人工。

### 3.5 停止与升级规则

- 迭代计数达 **5** 仍未通过 → 停止修订循环，进入终局报告流程（如实输出未通过及原因，见 task.md §6.5）；
- 同一阶段连续失败 3 次，或同一 FAIL 原因重复 2 轮 → 升级人工（可能是环境/数据系统性问题，继续盲修无意义）；
- Critic 判定 ESCALATE（发现疑似未来函数、数据完整性问题）→ 立即停全链；
- 时间盒：单次 run 总时长超过 30 分钟未完成 → 暂停并报告进度（各阶段产物保留，可续跑）。

### 3.6 中断恢复

Controller 启动时读取 manifest.json 找未完成 run，逐阶段核对检查点：
已完成且输入哈希一致的直接跳过；第一个不满足检查点的阶段作为续跑起点。
运行中的用户中断（Ctrl-C、会话重启）不丢任何已完成阶段。

### 3.7 限制（时间/成本/权限）

| 限制 | 数值 | 执行者 |
|---|---|---|
| 阶段超时 | 取数 120s；回测 300s；敏感性 600s | Controller 看门狗 |
| run 总时间盒 | 30 分钟 | Controller |
| LLM 调用预算 | 每 run：Generator ≤ 5 次、Critic ≤ 3 次；每调用 token 上限按模型默认 | Controller 记账，超限即升级 |
| 迭代上限 | 5 轮修订 | Controller 计数 |
| 工具权限 | 网络仅对②取数开放；Critic 只读无网络；Generator 仅 inbox/ 可写 | 文件系统与提示词双重约束 |
| 磁盘 | 单 run 产物预计 < 5 MB；runs/ 总量超 200 MB 时提示归档 | Controller 巡检 |

## 4. 核验与改进（要点 3）

### 4.1 Critic 独立评审的运作

- **上下文隔离**：Critic 在新会话/新上下文中运行，系统提示只含任务定义、
  验收标准、产物路径清单；**不可见** Generator 的推理过程、动机说明与历史对话。
- **输入白名单**：只读 metrics.json、auto_review.json、trades.csv 抽样
  （前/后各 20 行）、hypothesis.json、sensitivity/。
- **评审清单**（输出为结构化 verdict）：
  1. 五条验收标准逐条核对（引用 auto_review.json 的数值，自行复算抽查 ≥1 条）；
  2. 未来函数排查（信号-执行时序、复权口径、除息日附近的虚假信号）；
  3. 实现缺陷抽查（trades 与信号序列对得上吗、成本是否正确计提）；
  4. 稳健性审查（敏感性结果是否支持"结论不反转"）；
  5. 经济性判断：本轮改动相对上一 champion 是否实质改进。
- **防放水**：见 §2.3，数值门槛具有一票否决权。

### 4.2 人工批准节点

| 节点 | 触发 | 批准内容 |
|---|---|---|
| H1 | Generator 提案中规则结构变化（非单纯数值参数，如改单阈值为双阈值/加确认延迟） | 是否允许进入回测 |
| H2 | 修订循环收敛（PASS）或耗尽 5 轮 | 终局验收，决定定稿/再授权一轮 |
| H3 | 数据异常（缺口、as_of 倒挂、上市日确认失败） | 处置决定（修复数据/缩小窗口/中止） |

### 4.3 有界修订循环

- 修订预算 5 轮，由 Controller 硬计数；每轮 Generator 必须引用上一轮的
  critic_verdict.md 说明动机（task.md §6 预案顺序：85→80→确认延迟→结构变更）；
- 预算耗尽仍 FAIL → 停止，输出终局报告（未达标项、各轮指标轨迹、原因分析），
  **不允许**通过放宽验收标准凑通过。

### 4.4 对照固定基线的回归测试

- 买入持有基线指标由 Executor 用**同一数据快照**逐 run 重算，存入
  metrics.json 的 `baseline` 段——基线永远与策略同口径、同窗口；
- champion 回归：任何 v(k+1) 提案除对照基线外，还须不劣于 champion(v(k)) 的
  核心指标（年化、回撤），否则 Critic 可直接拒绝（防止迭代过程单调漂移变差）；
- 固定参照 run：task.md 验收以首轮数据快照下的基线为准，数据更新产生的
  "监控 run"不改动已定稿结论。
- **取舍说明**：champion 单调性约束会排除部分"先变差后变好"的探索路径，
  但在修订预算仅 5 轮且预案顺序已定的前提下，防指标漂移比保留探索空间
  更重要；确有探索必要时，H2 人工终局验收是逃逸阀——批准即可放行非常规路径。

### 4.5 裁决与记录

- 每轮产出不可变三件套：`auto_review.json`（数值判定）、`critic_verdict.md`
  （LLM 裁决原文）、`docs/iteration_log.md` 追加一行（run_id、改动摘要、
  五项指标、裁决、时间戳）；
- 裁决只能是 PASS / FAIL / ESCALATE 三值，理由逐条对应验收标准编号；
- 记录只追加不修改；终局报告引用记录原文。

### 4.6 版本记录与回滚

- hypothesis.json 自带版本号与父指针，run 链可追溯；
- `champion.json` 指向当前最优 run；回滚 = 将指针改指旧 run 并记录回滚原因，
  旧产物不删除（审计要求）；
- 迭代定稿后，champion run 的三件套连同报告一并 git 提交。

### 4.7 防未来信息泄露（as_of 纪律的落实机制）

1. **窗口裁切**：②取数阶段按 min(信号末日, 行情末日, 用户 as_of) 裁切窗口；
   行情覆盖晚于信号末日属正常（信号文件更新滞后），记录裁切标志即可；
   硬报错仅两种——信号与行情窗口无交集、用户 as_of 早于窗口起点，
   后者升级 H3；
2. **快照锁定**：回测阶段只允许读 `runs/<id>/data/` 内快照，网络权限在该阶段
   关闭；快照 manifest 记录 SHA-256，③回测前复核对不上即拒绝运行；
3. **时序白盒**：信号 join 按 DateTime 精确匹配，禁止向前填充信号；
   判定用 t 日收盘、t+1 执行在信号生成代码中单测覆盖；
4. **上市日自动确认**：起点取 max(上市首日, 信号首日)，来源与数值写入
   fetch_meta，杜绝手工写死导致的窗口错误；
5. **产物留痕**：每个含数字的产物标注 as_of；Critic 审查时逐项核对。

## 5. 数据流与错误处理（摘要）

- 原始输入只有两类：信号 xlsx（本地、版本受 git 管理）与 akshare 行情（外源、
  每轮快照留痕）；原始输入一律不改写，加工产物与原件分离；
- 除息日异常、信号贴 0/贴 100 的截断段、节假日缺口属**预期内数据特征**，
  在数据校验阶段出报告而非报错；缺 >5 个连续交易日才升级；
- 所有异常路径都落 state.json 的 `error` 段，恢复时优先展示给人工。
